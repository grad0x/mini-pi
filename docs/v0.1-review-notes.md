# Mini Pi v0.1 Final Review

Mini Pi v0.1 is a minimal Coding Agent Harness used to study and validate the
runtime boundaries behind modern coding agents. It is not a Pi clone and does
not aim to be a production coding-agent platform.

The v0.1 work proceeded in two acceptance stages:

1. a deterministic fix-bug demo that validates Harness composition and execution
   semantics repeatably;
2. a real OpenAI-compatible LLM experiment that replaces the deterministic model
   without changing Agent, Loop, Tool, Session, Event, Hook, or Policy semantics.

The second stage is important because it tests the Harness against a probabilistic
model rather than a scripted trajectory.

## Stable core

The implementation and experiments suggest that the following boundaries are
fundamental rather than Mini Pi-specific details.

### Agent and AgentLoop

`Agent` owns mutable runtime state and lifecycle. `AgentLoop` implements the
model -> tool -> observation -> model execution procedure.

Keeping state/lifecycle separate from the execution algorithm prevents the
Agent wrapper from accumulating every future concern such as steering,
streaming, retries, queues, or cancellation.

### Runtime state, durable history, execution context, and model input

Mini Pi separates:

```text
Session      = durable trajectory
AgentState   = mutable in-process runtime state
AgentContext = execution snapshot
ModelInput   = what the provider receives for one model call
```

These layers may contain similar data in the simplest configuration, but their
responsibilities are different. In particular, what the runtime knows does not
have to equal what the model sees.

### Provider port

`ModelClient` is owned by Agent Core. Provider-specific protocols are adapters
behind that interface.

The OpenAI-compatible experiment validated this boundary: replacing the
deterministic model with a real HTTP provider required no semantic changes to
Agent Core.

### Capability and policy

Tools expose capabilities to the model. Policies decide whether a requested
capability is allowed in the current environment.

This separation keeps environment operations reusable while allowing different
security and approval policies to be applied around the same Tool.

### Event and Hook

Events are observational. Hooks are interceptive.

```text
Event -> what happened?
Hook  -> should / how should it happen?
```

This boundary lets tracing, UI, telemetry, and evaluation observe execution
without becoming control dependencies, while Policy and approval logic can act
at explicit effect boundaries.

### Run and Turn

Explicit Run and Turn lifecycle boundaries are useful for tracing failures,
model calls, and Tool execution. The precise durable execution model may evolve,
but the need to name lifecycle boundaries remains.

## Implementation choices

The following are useful v0.1 implementations, not architectural requirements:

- JSONL as the SessionStore backend;
- `Object.freeze` and shallow defensive copies for selected snapshots;
- `RecentRunsContextCompiler` as one context projection strategy;
- exact-match `DenyCommandPolicy`;
- OpenAI Chat Completions-compatible HTTP as the first real provider adapter;
- persistence of a Run's messages after `Agent.prompt()` returns;
- the deterministic fix-bug model used by acceptance tests.

Future implementations can replace these choices while preserving the stable
boundaries above.

## Real LLM experiment

The deterministic fix-bug acceptance follows a deliberately scripted path. The
real LLM experiment used the same fixture, Tools, Session, Trace, and Policy but
replaced the model with an OpenAI-compatible provider.

The real run completed successfully with:

```text
5 Turns
5 model calls
6 Tool calls
final tests PASS
12 restored Session messages
```

Its trajectory was not the deterministic ideal path:

```text
Turn 1: run_command -> inspect workspace with ls/find
Turn 2: read_file x3 -> implementation, test, package.json
Turn 3: write_file -> minimal code fix
Turn 4: run_command -> node --test
Turn 5: final response
```

This is the most important v0.1 result: the Harness tolerated a different,
model-chosen trajectory without changing execution semantics.

## Experimental findings

### Probabilistic decision paths are real

A real model did not follow the minimal scripted trajectory. It explored the
workspace first and read an additional file before making the fix.

The Harness therefore cannot assume a fixed Tool order. It must provide stable
execution semantics around variable model decisions.

### Tool granularity changes model behavior

The real model used `run_command` as a workspace discovery capability because
Mini Pi does not expose a narrower `list_files` / `search_files` Tool.

This shows that Tool design is not only an ergonomics issue. A broad Tool such as
shell execution becomes an escape hatch through which the model can synthesize
many missing capabilities.

A more mature Harness should prefer narrow, explicit capabilities where useful
and treat unrestricted shell execution as a higher-risk effect boundary.

### Policy is not a sandbox

`DenyCommandPolicy` demonstrates the Hook / Policy mechanism, but exact command
matching is not a security boundary. Shell commands can be composed or expressed
in many equivalent forms.

Real model behavior makes this limitation concrete: once the model actively
uses shell composition, command-string denial cannot be treated as isolation.

Future security work should distinguish Policy, approval, and sandboxing rather
than treating them as the same mechanism.

### Session timestamps currently describe persistence time

`SessionRuntime` persists the Run's newly generated messages only after
`Agent.prompt()` returns. As a result, Session entry timestamps are created near
the persistence boundary rather than when each model or Tool event originally
occurred.

The append order is correct and the durable trajectory is restorable, but the
Session log is not an execution-timing trace. Trace events remain the source of
runtime lifecycle timing in v0.1.

### Model completion is not application verification

The real model ran `node --test`, observed a passing result, and then claimed
success. The example still ran the test suite again after the Agent Run.

This creates two separate layers:

```text
Agent verification
+
Application acceptance
```

A model's completion claim should not automatically be treated as the system's
verified outcome.

### Provider state and Harness Session are separate concerns

The first provider adapter uses Chat Completions-style requests where Mini Pi
supplies the required conversation context on each model call. Even when a
provider offers server-side conversation state, Mini Pi still needs its own
Session semantics for Tool trajectory, Policy results, recovery, branching,
audit, and Harness-specific metadata.

## Known design debt

### Run completed does not mean durable committed

`Agent` emits `run_finished(completed)` before `SessionRuntime` persists the new
messages. Agent Run completion therefore does not guarantee durable commit.

A future durable Harness needs an explicit durability boundary rather than
conflating successful Agent execution with committed work.

This is one of the clearest places where Mini Pi naturally approaches the
problems addressed by Pi Harness v2's durable Operation model.

### In-flight effects are not crash durable

Mini Pi does not record effect intent before Tool execution and cannot reconcile
an effect after a process crash. An external effect may have happened even when
the local process did not persist its result.

Future durable execution would need stronger effect / operation semantics and a
recovery protocol.

### `blocked` has coarse semantics

A policy denial and a fail-closed `beforeToolCall` infrastructure error can both
report `blocked: true`.

Future auditing may need a more precise disposition such as:

```text
allowed
denied
gate_error
execution_error
```

### Shell safety is intentionally incomplete

`run_command` is a real workspace Tool but not a security sandbox. Working
directory constraints and exact-match command policy do not isolate arbitrary
shell effects from the host environment.

### Context management is minimal

Mini Pi demonstrates context projection but does not yet implement mature
compaction, token budgeting, cache-aware context construction, or long-running
context recovery.

## v0.1 conclusion

Mini Pi v0.1 validates a useful distinction:

```text
Loop    -> how an Agent keeps running
Harness -> how an uncertain Agent execution is given stable boundaries
```

A minimal Harness needs more than a model/tool while-loop once the model can
produce real effects. State, Context, Tool capability, Session durability,
lifecycle events, interception, policy, provider boundaries, and independent
verification become separate engineering concerns because they change for
different reasons.

The real LLM experiment also shows why Harness complexity grows with maturity:
probabilistic paths, broad environment capabilities, durable side effects, and
verification pressure appear as soon as the scripted model is replaced by a
real one.

The next phase should therefore be chosen deliberately rather than by feature
accumulation. The strongest Harness-oriented research direction is durable
execution and effect recovery; Tool granularity, sandbox / approval, and richer
context management are adjacent pressures that should be studied against real
failure cases rather than added speculatively.
